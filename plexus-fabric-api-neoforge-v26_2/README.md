# plexus-fabric-api-neoforge-v26_2 — Fabric API Host Module for NeoForge 26.2

For Fabric API modules that cannot run normally alongside NeoForge even with Plexus Mod Loader's Mixin bridge, builds an in-house Fabric API implementation ("host module", `ADR-0031`) operating on top of `NeoForge 26.2.0.93` hooks.

## What This Module Does
- Builds Plexus Mod Loader's in-house Fabric API modules ("host modules", `ADR-0031`) on top of `NeoForge 26.2.0.93` hooks.
- Replaces modules that cannot run normally alongside NeoForge even with Plexus Mod Loader's Mixin bridge.
- Currently includes fifteen modules sharing the same public API as the corresponding modules in Fabric API `0.161.0+26.2`: `fabric-block-api-v1` (`3.1.0+plexus.neoforge.26.2`), `fabric-biome-api-v1` (`18.0.6+plexus.neoforge.26.2`, `always` replacing even if the original is loaded), `fabric-item-api-v1` (`14.5.0+plexus.neoforge.26.2`), `fabric-registry-sync-v0` (`7.1.1+plexus.neoforge.26.2`), `fabric-object-builder-api-v1` (`24.1.1+plexus.neoforge.26.2`), `fabric-content-registries-v0` (`11.3.2+plexus.neoforge.26.2`), `fabric-data-generation-api-v1` (`25.6.0+plexus.neoforge.26.2`), `fabric-menu-api-v1` (`2.0.17+plexus.neoforge.26.2`), client module `fabric-screen-api-v1` (`5.2.1+plexus.neoforge.26.2`), `fabric-sound-api-v1` (`2.0.5+plexus.neoforge.26.2`), `fabric-rendering-fluids-v1` (`6.0.4+plexus.neoforge.26.2`), `fabric-rendering-v1` (`25.3.3+plexus.neoforge.26.2`), `fabric-renderer-api-v1` (`14.1.4+plexus.neoforge.26.2`), `fabric-renderer-indigo` (`9.1.4+plexus.neoforge.26.2`, `always`), `fabric-model-loading-api-v1` (`8.0.17+plexus.neoforge.26.2`).
- Sources are the identically named modules from Sinytra Forgified Fabric API (https://github.com/Sinytra/ForgifiedFabricAPI, branch `26.2.x`, commit `40f8ce0`). These apply NeoForge-specific changes to Fabric API (`FabricMC`, https://github.com/FabricMC/fabric) modules.
- Changes in the block module include targeting Mixins at NeoForge's `IBlockExtension` and `IBlockStateExtension` instead of `Block`/`BlockState`, `EnchantmentPowerBridge` between Fabric and NeoForge enchantment powers, `LiquidBlockMixin` targeting NeoForge's `FluidInteractionRegistry.canInteract`, and `EnchantmentMenuMixin` targeting NeoForge's `EventHooks.onEnchantmentLevelSet`.
- Forgified Fabric API's own changes to the item module include Mixins targeting NeoForge's `IItemExtension` and `IItemStackExtension` (`IItemExtensionMixin`, client `IItemExtensionClientMixin`), tooltip processing via NeoForge's `ItemTooltipHandler`, and anvil and enchantment checks based on NeoForge hooks (`AnvilMenuMixin`, `EnchantCommandMixin`, `EnchantRandomlyFunctionMixin`).
- Plexus Mod Loader's changes to the item module (excluding formatting cleanup):
  - Removes Forgified Fabric API's `FabricItemImpl` (a NeoForge `@Mod` class), and wraps the `ModLoader.postEvent` call inside NeoForge's `ItemTooltipHandler.init` with a new Mixin `ItemTooltipHandlerMixin` to register `ItemComponentTooltipProviderRegistryImpl` after posting the event.
  - `ClientItemEventHooks` is a Fabric `ClientModInitializer` (client entry point) that registers listeners on `NeoForge.EVENT_BUS`.
  - `DataComponentMapBuilderMixin` explicitly declares `getOrDefault` because NeoForge's `IDataComponentMapBuilderExtensions` and `DataComponentGetter` both provide default methods.
  - `IItemExtensionMixin.isPrimaryItemFor` reflects explicit `EnchantmentEvents.ALLOW_ENCHANTING` responses first.
- The header of each file specifies the source file, commit, and Plexus Mod Loader's modifications.
- The license is `Apache License 2.0`, and the jars contain `LICENSE_fabric-api` (both projects share identical text, with no `NOTICE` file).

- biome module: A Plexus Mod Loader build for NeoForge constructed directly from Fabric API's own source (`FabricMC`), rather than from Forgified Fabric API. The original module uses Guava's memoizing `Supplier` for `ChunkGenerator.featuresPerStep`, but NeoForge places a `Lazy` there and casts it to `Lazy` when executing biome modifiers (`ClassCastException`), so instead of writing to the field, it calls NeoForge's `ChunkGenerator.refreshFeaturesPerStep()`. Furthermore, NeoForge's biome getters read generation settings and modified climate, effects, and spawn settings from `ModifiableBiomeInfo` created by NeoForge prior to Fabric API modifications. After Fabric API modifies biomes, `NeoForgeBiomeInfo` attaches a new `ModifiableBiomeInfo` to the biome with the Fabric API-modified state as its original (`BiomeAccessor` mixin sets the field), allowing NeoForge's own modifiers to start on top of it. This is the same approach as in the 26.3 README.
- registry-sync module: Strips the NeoForge mod bus listener in `FabricRegistryInit` from FFAPI's counterpart module, and a new `RegistryManagerMixin` wraps `DataPackRegistryEvent.NewRegistry.process()` and the posting of `ModifyRegistriesEvent` inside NeoForge's `RegistryManager.postNewRegistryEvent`.
- object-builder module: Removes FFAPI's `FabricObjectBuilderImpl` (a NeoForge `@Mod` class, listener for `FMLCommonSetupEvent` and `EntityAttributeModificationEvent`), and a new `GameDataMixin` applies attribute modifications (`FabricDefaultAttributeRegistry.MODIFY`) and added valid blocks (`FabricBlockEntityType.addValidBlock`) in `GameData.freezeData` after both NeoForge registration (`GameData.postRegisterEvents`) and Fabric mod initialization have completed. On the server, Fabric mod initialization precedes NeoForge registration; on the client, it comes after. `FabricDefaultAttributeRegistryImpl` modifies values in the NeoForge map (`CommonHooks.FORGE_ATTRIBUTES`, new `CommonHooksAccessor`) that `DefaultAttributes.getSupplier` reads first. The two client mixins for the sign editing screen from the original are omitted as in FFAPI (NeoForge patches already handle modded wood types by using `Identifier.parse` instead of `Identifier.withDefaultNamespace`).
- content-registries module: FFAPI migrated composting (`CompostableRegistry`) and Hero of the Village gifts (`VillagerInteractionRegistries.registerGiftLootTable`) to NeoForge data map lookups (`BaseMappedRegistry.getData`, new `BaseRegistryMixin` and `DataMapModifications`), fuels to NeoForge `DataMapHooks.populateFuelValues` (`DataMapHooksMixin`), axe stripping to NeoForge `AxeItem.getAxeStrippingState`, and hoe tilling to NeoForge `BlockToolModificationEvent`, while delegating fluid swimming, drowning, jumping, and movement to NeoForge `FluidType` (`ContentRegistriesImpl` aggregating per-`FluidType` flows in `EntityFluidInteraction` into tags, `EntityFluidInteractionMixin`). Plexus Mod Loader replaces FFAPI's `@Mod` class `ContentRegistriesImpl` with a Fabric `main` entry point; since FML does not read this module, instead of `@EventBusSubscriber` on `TillableBlockRegistry`, that entry point registers the listener via `NeoForge.EVENT_BUS.register(TillableBlockRegistry.class)`. `Block2ObjectMap` and `Item2ObjectMap`, which FFAPI moved to `fabric-api-base`, are kept in their original Fabric API location (this module). The `fabric-api-base` alongside Plexus Mod Loader comes from Fabric API and lacks these two.
- data-generation module: Because NeoForge adds identically named `remove` methods to `TagAppender`, `BlockItemTagAppender`, and `TagBuilder`, FFAPI omits the mixins implementing tag removal (`BlockItemTagAppenderMixin`, `TagAppenderMixin$TagAppender1Mixin`, `TagBuilderMixin`, and removal/replacement injections in `TagsProviderMixin`) and has `FabricTagAppender` inherit NeoForge's `ITagAppenderExtension`. Recipe output is wrapped with NeoForge's condition-accepting `RecipeOutput.accept`, and model generators are wrapped with NeoForge's `ModelProvider.registerModels`. Plexus Mod Loader implements `FabricTagAppender.remove(ResourceKey...)`, `removeAll`, and `removeTag`—which still threw "Implemented via mixin" exceptions in FFAPI—using NeoForge's `remove`.
- menu module: NeoForge relocates the body of `ServerPlayer.openMenu(MenuProvider)` to `openMenu(MenuProvider, Consumer)`, and sends extra data if present via its own `AdvancedOpenScreenPayload`, received on the client by the menu type's `IContainerFactory`. Fabric API's `ServerPlayerMixin` (menu storing `@Inject`, `closeContainer` and packet `@Redirect`) did not match the relocated body, resulting in `224`. FFAPI strips Fabric's custom open packets (`Networking`, client `ClientNetworking`), unwraps `ExtendedMenuProvider` wrapped in `SimpleMenuProvider` in `openMenu(MenuProvider)` (`@ModifyArg`), and in `openMenu(MenuProvider, Consumer)`, replaces writing additional data after menu creation with writing `getScreenOpeningData` using the menu type's codec (`@ModifyVariable`). `ExtendedMenuType` reads data via NeoForge's `IContainerFactory` to create the menu, and `MenuProviderMixin` bridges `shouldCloseCurrentScreen` to NeoForge's `shouldTriggerClientSideContainerClosingOnOpen`. Plexus Mod Loader replaced `javax.annotation.Nullable`, which is not on the classpath, with jspecify's annotation.
- screen module: NeoForge draws screens via `ClientHooks.extractScreen` and notifies keyboard and mouse input through its own `ScreenEvent`. Fabric API's `GuiMixin` (wrapping `Screen.extractRenderStateWithTooltipAndSubtitles` in `Gui.extractRenderState`), `KeyboardHandlerMixin`, and `MouseHandlerMixin` did not match, resulting in `224`. FFAPI omits those mixins, and `ScreenEventHooks` forwards NeoForge `ScreenEvent`s (render, keyboard, mouse) to Fabric events. Since FML does not read `@EventBusSubscriber` on Fabric mods, Plexus Mod Loader strips the annotation, and the new client entry point `ScreenApiClientInit` registers it via `NeoForge.EVENT_BUS.register(ScreenEventHooks.class)`.
- sound module: In `SoundEngine.play`, NeoForge calls its own default method `SoundInstance.getStream(SoundBufferLibrary, Sound, boolean)` instead of `SoundBufferLibrary.getStream`. FFAPI's `SoundInstanceMixin` overwrites (`@Overwrite`) that default method and passes execution to `FabricSoundInstance.getAudioStream`.
- rendering-fluids module: NeoForge replaces the `HalfTransparentBlock` check in `FluidRenderer.tesselate` with `BlockState.shouldDisplayFluidOverlay`. FFAPI's `FluidRendererMixin` replaces the result of that call with `FluidRenderingRegistryImpl.isBlockTransparent(block, original)` (verified call and local variable `faceState` in 26.2.0.93 via `javap`).
- rendering, renderer-api, indigo, and model-loading modules: NeoForge draws the HUD using its own GUI layers, registers picture-in-picture renderers and block models via its own events and extensions, and provides different parameters to `BlockStateModel.collectParts`, `hasMaterialFlag`, and `SectionCompiler.compile` wrapped by Fabric API. Using FFAPI's counterpart modules, Plexus Mod Loader modified the following:
  - Removes FFAPI's `@Mod` class `FabricRenderingImpl`, and new mixins `ClientHooksMixin` (`ClientHooks.gatherPictureInPictureRenderers`) and `GuiLayerManagerMixin` (`GuiLayerManager.initModdedLayers`) wrap `ModLoader.postEvent` calls to add Fabric registrations after NeoForge mods receive the event.
  - `RenderPipelineBuilderMixin` wraps the entirety of `buildSnippet` with `@WrapMethod` instead of `@WrapOperation` on the `Snippet` constructor (host checks consider `NEW` without a constructor descriptor as mismatched regardless of handler, and specifying the descriptor causes Mixin to fail to find the injection point at runtime).
  - `SubmitNodeStorageMixin` does not implement `SubmitNodeCollector` and shadows (`@Shadow`) `order(int)`. Because NeoForge's `SubmitNodeStorageExtension` already inherits `SubmitNodeCollector`, it is the same method and avoids default method conflict detection by host checks.
  - `VanillaBlockModelPartEncoder` retains `TriState.fromVanilla`, which FFAPI added to its own `fabric-api-base`, as its own method.
  - `HudElementRegistryImpl` connects Fabric's `INFO_BAR` to NeoForge's `CONTEXTUAL_INFO_BAR_BACKGROUND` (verified `Hud.registerVanillaLayers` via `javap`).
  - indigo loads when the original renderer-api changes, but is marked as `always` in the index to replace it. `SectionCompilerMixin` in renderer-api routes all blocks in the level to Indigo, and only FFAPI's Indigo preserves NeoForge's level-based face culling, light emission, dynamic tinting, and baked vertex colors. The rationale is based on code comparison rather than test output lines (follow-up to `ADR-0031`).
- Compiler configuration: The compiler for this project disables the varargs lint (`-Xlint:-varargs`). This is because `BiomeSelectors` in the biome API passes generic varargs directly, which matches upstream Fabric API.
- The build applies `transitive-*` class tweaker lines from other host modules on which a host module depends, and for rendering and renderer-api, applies class tweakers from Fabric API's `fabric-transitive-access-wideners-v1` (`8.1.4+67c847259e`) at compile time (same as Loom).- Upstream object-builder loads without `224` alongside NeoForge, but attribute modifications do not reach the game (test mod `fabric-object-builder`: zombie max health 20.0, whereas Fabric standalone is 42.0). Therefore, it is marked as `always` in the index to replace it even if the original loads.

## What It Owns
- Source set structure: `src/fabricBlockApiV1`, `src/fabricBiomeApiV1`, `src/fabricItemApiV1`, `src/fabricRegistrySyncV0`, `src/fabricObjectBuilderApiV1`, `src/fabricContentRegistriesV0`, `src/fabricDataGenerationApiV1`, `src/fabricMenuApiV1`, `src/fabricScreenApiV1`, `src/fabricSoundApiV1`, `src/fabricRenderingFluidsV1`, `src/fabricRenderingV1`, `src/fabricRendererApiV1`, `src/fabricRendererIndigo`, `src/fabricModelLoadingApiV1`. renderer-api compiles against rendering; indigo and model-loading compile against rendering and renderer-api. data-generation also compiles against the registry-sync source set. object-builder compiles against the outputs of the registry-sync source set (`HostModule.dependsOn`).
- Fabric mod jars: each module's `fabric.mod.json`, Mixin configurations (`fabric-block-api-v1.mixins.json`, `fabric-item-api-v1.mixins.json`, `fabric-item-api-v1.client.mixins.json`), and class tweakers (`fabric-block-api-v1.classtweaker`, `fabric-item-api-v1.classtweaker`).
- The `custom` field `plexusmodloader:host-module` in `fabric.mod.json` (`host` `neoforge`, `minecraft` `26.2`, `replaces` respective module versions).
- Implementation source code tailored to NeoForge hooks: `fabric-block-api-v1` and `fabric-item-api-v1` implementation code (`net.fabricmc.fabric.api.block.v1.*`, `net.fabricmc.fabric.api.item.v1.*`, `net.fabricmc.fabric.api.client.item.v1.*`, `net.fabricmc.fabric.impl.*`, `net.fabricmc.fabric.mixin.*`).
- Gradle build tasks: `installNeoForgeClient`, `<sourceSet>CompileGame`, `<sourceSet>Jar`, `hostModuleIndex`, `hostModuleResources`.
- Build artifact jars (fifteen jars under `META-INF/plexusmodloader/host-modules/neoforge-26.2.0.93/`) and the index file `META-INF/plexusmodloader/host-modules.properties` (keys `neoforge-26.2.0.93.<mod ID>`, and `neoforge-26.2.0.93.<mod ID>.always=true` for modules that replace even if the original is loaded).
- Consumable configuration `hostModuleElements` delivering artifacts to `plexus-bridge-fabric`.

## What It Does Not Do
- Does nothing in the absence of NeoForge or on other NeoForge releases.
- Not intended for `MinecraftForge`.
- Does not download or require Forgified Fabric API.
- Does not reimplement modules that already run via the bridge.
- Does not place jars directly onto Plexus Mod Loader's classpath.

## Representative Flow
1. The `hostModuleResources` task places jars into `META-INF/plexusmodloader/host-modules/neoforge-26.2.0.93/` and writes the index `META-INF/plexusmodloader/host-modules.properties`. The consumable configuration `hostModuleElements` delivers this to `plexus-bridge-fabric` to include it only in that jar.
2. At runtime (`plexus-runtime-impl`), when `NeoForge 26.2.0.93` is the host, `HostPatchCheck` first marks original modules that do not match the patches as `PLEXUS-COMPAT-224`.
3. For each module omitted via `224` or marked as `always`, `HostModules.replaceLeftOut` extracts the host module indexed for that host release, evaluates it like a regular mod file, places it in the original module's position, and logs the replacement.
4. `HostPatchCheck` is re-run against the replaced results to verify that the host modules also conform to the patches.
5. During the link verification step (`ModLinkVerifier`), the host's patched game and loader jars are read before the vanilla jar to verify links.

## Known Limitations
- Built exclusively for `NeoForge 26.2.0.93`.
- Must be rebuilt and re-verified when a new NeoForge release comes out.
- Window task `neoForgeFabricClientProbe` (test mod `fabric-client-probe`) verifies tooltip lines, screen events, extended menu screens and opening data, water fluid handlers, and streaming sound `getAudioStream` on the client, matching output lines from Fabric standalone (`fabricClientProbe`). Rendering results (HUD elements, picture-in-picture, FRAPI meshes, Indigo lighting, model plugins) have not been visually inspected, and there are no test mods verifying them. The client-side ordering of object-builder (Fabric initialization after NeoForge registration) has also not been verified via window tasks.
- `sodium-frapi.mixins.json` from Sodium for NeoForge is not applied because FML cannot see Fabric mods, failing with "required mod 'fabric_renderer_api_v1' is missing", and Indigo also fails to see Sodium's `contains_renderer` property and registers itself. Whether FRAPI block models from Fabric mods render as in Fabric alongside Sodium has not been verified.
- FFAPI was built against NeoForge 26.2.0.88. On 26.2.0.93, verification only covers compilation, host checks, and class loading.
- Fabric mods requiring module versions newer than the version of each module are handled by standard version checks.
- content-registries delegates Fabric fluid behaviors (`FluidBehavior`)—swimming, drowning, fluid jumping, fluid movement, and boating—to NeoForge `FluidType` instead of replacing them via Fabric mixins, as FFAPI does. It assigns a NeoForge `FluidType` (`FabricFluidType`: delegating `canSwim`, `canDrownIn`, `supportsBoating`, and `move` to `FluidBehavior`; `NeoForgeFluidTypes`; `FluidMixin` at the head of `Fluid.getFluidType`) to each Fabric fluid tag possessing a `FluidBehavior`, and maps water and lava tags to NeoForge's own types. Previously, when fluids from Fabric mods flowed, NeoForge stopped the server with "Mod fluids must override getFluidType.". Drowning, swimming, sinking, and boating are verified by `neoForgeFabricApiGameTest` (26.2, 26.3) and window task `neoForgeFluidClient`.
- data-generation only runs the tag provider in game tests. Recipe, loot, model, and language providers, as well as data generation execution (`-Dfabric-api.datagen`), have not been verified alongside NeoForge. Because NeoForge's server `Main` checks the EULA before the creation of `DedicatedServerSettings` where Fabric API initiates data generation, Plexus Mod Loader's verification (not agreeing to the EULA) does not reach that point. Actual data generation in Fabric standalone is verified by `fabricDatagenRun`. Tag files generated alongside NeoForge write removal lists to both NeoForge's `remove` and `fabric:remove` (Fabric standalone writes only `fabric:remove`).
- menu verifies the server side (menus opening and requesting opening data) in game tests, and verifies on the client via window task `neoForgeFabricClientProbe` that the client creates menus from NeoForge's open packet (opening data 42) and opens screens registered with `MenuScreens.register`. Because it uses NeoForge's `AdvancedOpenScreenPayload` instead of Fabric's open packet (`fabric-menu-api-v1:open_screen`) used in Fabric standalone, NeoForge must also be present on the client.
