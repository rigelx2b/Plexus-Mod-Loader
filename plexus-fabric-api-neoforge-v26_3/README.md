# plexus-fabric-api-neoforge-v26_3 — Fabric API Host Module for NeoForge 26.3

For Fabric API modules that cannot run as-is alongside NeoForge even with Plexus Mod Loader's Mixin bridge, this builds an in-house Fabric API implementation ("host module", `ADR-0031`) that operates on top of `NeoForge 26.3.0.98` hooks. The 26.2 version is [`plexus-fabric-api-neoforge-v26_2`](../plexus-fabric-api-neoforge-v26_2/README.md).

## What this module does
- Builds seventeen modules with the same public API as the corresponding modules in Fabric API `0.165.0+26.3`: `fabric-block-api-v1`(`3.1.0+plexus.neoforge.26.3`), `fabric-biome-api-v1`(`20.1.1+plexus.neoforge.26.3`, `always`), `fabric-item-api-v1`(`14.8.0+plexus.neoforge.26.3`), `fabric-registry-sync-v0`(`8.0.4+plexus.neoforge.26.3`), `fabric-object-builder-api-v1`(`24.1.12+plexus.neoforge.26.3`, `always` replacing even if the original is loaded), `fabric-content-registries-v0`(`15.0.6+plexus.neoforge.26.3`), `fabric-resource-conditions-api-v1`(`6.2.0+plexus.neoforge.26.3`), `fabric-data-generation-api-v1`(`27.4.2+plexus.neoforge.26.3`), `fabric-menu-api-v1`(`2.0.30+plexus.neoforge.26.3`), `fabric-entity-events-v1`(`6.0.4+plexus.neoforge.26.3`), client modules `fabric-screen-api-v1`(`5.2.4+plexus.neoforge.26.3`), `fabric-sound-api-v1`(`2.0.7+plexus.neoforge.26.3`), `fabric-rendering-fluids-v1`(`6.0.6+plexus.neoforge.26.3`), `fabric-rendering-v1`(`27.2.0+plexus.neoforge.26.3`), `fabric-renderer-api-v1`(`17.0.17+plexus.neoforge.26.3`), `fabric-renderer-indigo`(`9.1.25+plexus.neoforge.26.3`, `always`), `fabric-model-loading-api-v1`(`8.0.37+plexus.neoforge.26.3`).
- Sinytra Forgified Fabric API does not have a 26.3 branch. Therefore, the source was created by applying Fabric API's `0.161.0+26.2`→`0.165.0+26.3` changes via a three-way merge onto the 26.2 host module (FFAPI `26.2.x` commit `40f8ce0` + Plexus Mod Loader changes) (merged after aligning to the same palantir formatting). Each file's header notes its provenance and changes. Files newly introduced in 26.3 were brought from Fabric API `0.165.0+26.3`.
- Differences from the 26.2 version:
  - registry-sync: NeoForge 26.3 uses `NewDatapackRegistryEvent` (which receives world and reloadable registries separately) instead of `DataPackRegistryEvent.NewRegistry`. `DynamicRegistriesImpl` implements the 26.3 public API (`getAllDynamicRegistries`, `getWorldRegistries`, `getReloadableRegistries`, `registerReloadable`) on top of this event and the game's registry list (which NeoForge's patch populates with registries from all loaders). The new `NewDatapackRegistryEventAccessor` creates and processes the event. `FabricRegistryInit`'s `onInitialize` only assigns attributes (`SYNCED`, the new `SAVE_DATA_VALIDATED`) to built-in registries. Synchronization is handled by NeoForge. 26.3's saved data validations (`MinecraftServerMixin`, client `WorldOpenFlowsMixin`, etc.) are left as-is. `ReloadableServerRegistriesMixin` and `RegistriesDatapackGeneratorMixin`, which replace the game's registry list with Fabric copies, are omitted because alongside NeoForge, the game list already contains all registries.
  - biome: A build for NeoForge made by Plexus Mod Loader from Fabric API's own source rather than from Forgified Fabric API (the same approach as `ForgeBiomeInfo` in the MinecraftForge host module). The original module uses Guava's memoizing `Supplier` for `ChunkGenerator.featuresPerStep`, but NeoForge puts a `Lazy` there and casts it when executing biome modifiers (`ClassCastException`), so this was adapted to NeoForge's `ChunkGenerator.refreshFeaturesPerStep()`. Furthermore, after Fabric API modifies biomes, `NeoForgeBiomeInfo` replaces the biome's `ModifiableBiomeInfo` with a new `ModifiableBiomeInfo` whose original state is the state modified by Fabric API (`BiomeAccessor` mixin sets the field), allowing NeoForge's own modifiers to start on top of it.
  - item: The tooltip order API accepts `TooltipProvider.Getter`. It is registered with NeoForge 26.3's `TooltipAppender.createComponentAppender(type, getter)`. The new block transformation APIs (`BlockTransformerEvents`, `BlockTransformerHelper`) and `FishingHookMixin` are kept as in the original (matching the NeoForge 26.3 patch). `FirstPersonHandsAndItemsMixin` (`ItemInHandRendererMixin` in 26.2) is omitted, following FFAPI. `ResourceUtil` also treats datapacks from NeoForge mods as mod sources (FFAPI's condition).
  - content-registries: Fabric API 26.3 removed the composting, fuel, stripping, tilling, flattening, decorated pot, brewing, and villager food APIs from this module, so those parts from the 26.2 version (FFAPI's compost/fuel datamap wiring, `TillableBlockRegistry` listener) are also removed. In 26.3, the class tweaker is eliminated and `EntityMixin` directly implements `EntityFluidExtension`. Oxidation stages and waxed blocks also register axe stripping via the item module's block transformer (`BlockTransformerHelperImpl`), so it compiles against the item source set. Adaptations to NeoForge 26.3: because `EntityFluidInteraction` collects flows into `CurrentAccumulator` per `FluidType` (field `currentAccumulators`), `ContentRegistriesImpl` and the new `EntityFluidInteractionCurrentAccumulatorAccessor` read it, and because `EntityFluidInteraction.update` returns `boolean`, `EntityMixin`'s wrapper is adjusted accordingly. NeoForge 26.3's `DataMapHooks` looks up oxidation stages and waxed blocks only in datamaps (26.2 fell back to the game's map). Therefore, `DataMapModifications` returns the pairs registered by Fabric mods as `OXIDIZABLES` and `WAXABLES` datamap values, and the new `DataMapHooksMixin` adds those pairs after NeoForge rebuilds the reverse maps (lightning, `WeatheringCopper.getFirst`).
  - resource-conditions: There is no host module in 26.2 (the original ran via bridge). The 26.3 version is the module from Fabric API `0.165.0+26.3` as-is, with only `SimpleJsonResourceReloadListenerMixin` coming from FFAPI. Fabric API 26.3 checks JSON data conditions in `Codec.parse` within vanilla 26.3's `prepare` (the handler being an instance method reading `this.lister`) and skips them in the storage lambda `lambda$prepare$0`, but NeoForge 26.3's `prepare` instead calls static `scanDirectory` (which returns a map) and parses with conditional codecs there. Therefore, following FFAPI, it wraps `scanDirectory`'s parsing and returns NeoForge's skip value `DataResult.success(Optional.empty())` if conditions are not met. Because 26.3 loads recipes as registries, FFAPI's target `scanDirectoryWithModifier` is omitted. The registry path (`RegistryLoadTaskPendingRegistrationMixin`) executes before NeoForge's conditional codec calls via `NeoForgeInjectionPoints` rules, just like the original.
  - data-generation: Merged Fabric API 26.3 changes into the 26.2 host module. The new public interface in 26.3, `FabricTagBuilder`, inherits from NeoForge's `ITagBuilderExtension`, and the removal list is that of NeoForge's `TagBuilder` (the new `TagBuilderMixin` only adds the interface). `withConditions` implements `RecipeOutput.accept` taking NeoForge's condition parameter. `BlockLootSubProviderMixin.onlyVanillaBlocks` and `EntityLootSubProviderMixin.onlyVanillaEntities` added by Fabric API 26.3 (making vanilla loot generators inspect only the `minecraft` namespace) are omitted because those calls do not exist in the NeoForge 26.3 patch, keeping FFAPI's empty mixins instead. NeoForge 26.3's `run` iterates over `getKnownBlocks` and `getKnownEntityTypes`, and `VanillaBlockLoot` and `VanillaEntityLoot` already return only the `minecraft` namespace.
  - menu: Identical to the 26.2 version (NeoForge 26.3's `openMenu`, `IContainerFactory`, and `IMenuProviderExtension` are identical to 26.2). The only change in Fabric API 26.3 was the JavaDoc example in `ExtendedMenuType`, so only that file had FFAPI's code changes reapplied to the 26.3 file.
  - entity-events: There is no host module in 26.2 (the original ran via bridge). The 26.3 version is the module from Fabric API `0.165.0+26.3` as-is, with only `ServerPlayerMixin`'s `redirectSleepDirection` and `hasNoMonstersNearby` targeting `lambda$startSleepInBed$0(BlockState, BedRule, BlockPos, boolean)`, to which NeoForge 26.3 moved the `startSleepInBed` checks, and accepting its parameters (Fabric 26.3's handler received `(AbstractBedBlock, BlockState, BedRule, BlockPos)` from `startSleepInBed`, which the bridge could not relocate). Compiles against `asm` because the elytra mixin uses ASM constants.
  - screen, sound, rendering-fluids: Identical code to the 26.2 version. Across Fabric API 26.2→26.3, these three modules changed only in documentation (JavaDoc examples, required `fabricloader` version), so the changed files were taken directly from Fabric API `0.165.0+26.3`. Confirmed via `javap` that `ClientHooks.extractScreen`, `SoundInstance.getStream`, and `FluidRenderer.tesselate`'s `shouldDisplayFluidOverlay` and local variable `faceState` in NeoForge 26.3.0.98 are identical to 26.2.
  - rendering, renderer-api, indigo, model-loading: Three-way merged Fabric API 26.3 changes into the 26.2 host module (model-loading has identical code; only `fabric.mod.json` changed). Manually resolved: rendering `GameRendererMixin` (omitted `guiRendererReady` following FFAPI), `GuiRendererMixin` (removed picture-in-picture pool again), `RenderPipelineBuilderMixin` (retained `@WrapMethod` from the 26.2 version, receives 26.3's `withSnippet` callback), package rename in class tweaker (`com/mojang/blaze3d/pipeline`→`com/mojang/renderpearl/api/pipeline`), renderer-api `SubmitNodeStorageMixin` (26.3 signature). Fabric API 26.3's new `block.particle.LevelExtractorMixin` is not included. NeoForge 26.3's `LevelExtractor.getViewBlockingState` only calls its own `getViewBlockingStateAndPos`, for the same reason FFAPI omitted `ScreenEffectRendererMixin` in 26.2. `HudElementRegistryImpl` connects 26.3's new `INFO_BAR_FOREGROUND` to NeoForge's `CONTEXTUAL_INFO_BAR`. rendering and renderer-api compile with Fabric API 26.3's `fabric-transitive-access-wideners-v1` (`8.1.17+e2f63d3e5d`) class tweaker applied.
  - object-builder: Fabric API 26.3 moved access widening for `PoiTypes.register` to `fabric-transitive-access-wideners-v1`. Because this build does not compile against that module, it retains that line in its own class tweaker.

## What it owns
- Source sets `src/fabricBlockApiV1`, `src/fabricBiomeApiV1`, `src/fabricItemApiV1`, `src/fabricRegistrySyncV0`, `src/fabricObjectBuilderApiV1`, `src/fabricContentRegistriesV0`, `src/fabricResourceConditionsApiV1`, `src/fabricDataGenerationApiV1`, `src/fabricMenuApiV1`, `src/fabricEntityEventsV1`, `src/fabricScreenApiV1`, `src/fabricSoundApiV1`, `src/fabricRenderingFluidsV1`, `src/fabricRenderingV1`, `src/fabricRendererApiV1`, `src/fabricRendererIndigo`, `src/fabricModelLoadingApiV1`, along with each module's `fabric.mod.json`, Mixin configuration, and class tweakers.
- The `custom` field `plexusmodloader:host-module` in `fabric.mod.json` (`host` `neoforge`, `minecraft` `26.3`, `replaces` each module version).
- Build artifact jars (`META-INF/plexusmodloader/host-modules/neoforge-26.3.0.98/`) and the index for this module. `plexus-bridge-fabric` combines this with the 26.2 version's index into a single file in the jar (`hostModuleIndex` task).
- The consumable configuration `hostModuleElements` delivering artifacts to `plexus-bridge-fabric`.

## What it does not do
- Does nothing when NeoForge is absent or on releases other than NeoForge 26.3.0.98.
- Not intended for MinecraftForge.
- Does not download or require Forgified Fabric API.

## Dependencies
- Minecraft `26.3` (`plexusCompileMinecraft=26.3`).
- The patched client jar created by the `installNeoForgeClient` task using NeoForge `26.3.0.98`'s own installer (verified with SHA-1 `c3d8feb159c1abeb89af6e10e1be7b6e080d0eb9`) (`~/.gradle/caches/plexus-neoforge/26.3.0.98/client`, requires network on first use).
- `compileOnly`: NeoForge `26.3.0.98` universal jar, FML 12 loader, NeoForge event bus, mergetool API, Fabric Loader, Mixin, MixinExtras, `fabric-api-base`, `fabric-resource-loader-v1`, `fabric-lifecycle-events-v1`, jspecify, JetBrains annotations. object-builder compiles against the registry-sync source set, content-registries compiles against the item source set, and data-generation compiles against the registry-sync and resource-conditions source sets. data-generation also compiles against Fabric API's tag, convention-tags, recipe, and resource-conditions module jars (26.2 version).

## Build and test
```powershell
.\gradlew.bat :plexus-fabric-api-neoforge-v26_3:assemble
.\gradlew.bat -PplexusMinecraft=26.3 :plexus-bootstrap:fabricApiGameTest :plexus-bootstrap:neoForgeFabricApiGameTest
.\gradlew.bat -PplexusMinecraft=26.3 :plexus-bootstrap:corpusFabricNeoForge
```
- In 26.3, `fabricApiGameTest` (Fabric standalone) and `neoForgeFabricApiGameTest` (alongside NeoForge) verify that test mods `fabric-block-item`, `fabric-dynamic-registry`, `fabric-object-builder`, `fabric-oxidizable-blocks`, `fabric-resource-conditions`, `fabric-data-generation`, `fabric-menu`, and `fabric-entity-events` produce the same 30 lines. `neoForgeFabricApiGameTest` now includes `fabric-biome-modification` and 4 biome lines (`minecraft:patch_cactus_desert: true` in Nether Wastes generation settings, 26.3's flattened Nether generator, Plains default temperature `1.25`, and Plains temperature transmitted to the client `1.25`). `fabric-api-events` is not used in 26.3 (it was used for 26.2).

## Representative flow
Same as `plexus-fabric-api-neoforge-v26_2`. The host key is `neoforge-26.3.0.98`.

## Known limitations
- Exclusively for `NeoForge 26.3.0.98`. It must be rebuilt and verified when a new NeoForge release comes out.
- content-registries assigns a NeoForge `FluidType` (`FabricFluidType`: delegates `canSwim`, `canDrownIn`, `supportsBoating`, `move` to `FluidBehavior`; `NeoForgeFluidTypes`; `FluidMixin` at the head of `Fluid.getFluidType`) for each Fabric fluid tag that has a `FluidBehavior`. Water and lava tags map to NeoForge's own types.
- On the client, `fabric-lifecycle-events-v1` is loaded via the `handleUpdateTags` rule of `NeoForgeInjectionPoints` starting from 2026-11-01 (the tag load event executes before `CreativeModeTabs.allTabs()`, where NeoForge rebuilds search trees). Not verified in a window.
- data-generation verifies only tag providers via gametests. The actual data generation run alongside NeoForge (`-Dfabric-api.datagen`) cannot be validated because NeoForge's server `Main` checks the EULA first (same as the 26.2 version). Actual data generation on Fabric standalone (tags, loot, translations, recipes, and advancements) is verified by `fabricDatagenRun`.
- menu verifies the server side in gametests, and verifies on the client via the window task `neoForgeFabricClientProbe` (test mod `fabric-client-probe`) that the client creates a menu from NeoForge's open packet (open data 42) and opens the screen. The same task also verifies item tooltip lines, screen events, water fluid handlers, and streaming sounds against the same lines as Fabric standalone (`fabricClientProbe`).
- Rendering results (HUD elements, picture-in-picture, FRAPI meshes, Indigo lighting, model plugins) have not been visually inspected and have no test mods. indigo's `always` is based on code comparison (26.2 version README). Sodium's FRAPI wiring for NeoForge is not applied, same as in the 26.2 version.
- In the 26.3 gametest server, the Nether is flattened and features are not placed.
- Since there is no 26.3 version of FFAPI, changes in 26.3 were adapted directly by Plexus Mod Loader. Saved data validation screens in the window (client) were not verified (tooltip lines are verified by `neoForgeFabricClientProbe`).
